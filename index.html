Start MongoDB local or Atlas

Use mongodb-runner local


# Install once
npm install -g mongodb-runner

# Standalone server on the default port
mongodb-runner start

# Or a replica set (required for transactions)
mongodb-runner start -t replset

# List what's running, then stop everything
mongodb-runner ls
mongodb-runner stop --all

# Run a command with MONGODB_URI pre-set
mongodb-runner exec -t standalone -- sh -c 'python manage.py migrate'

Requires Node.js ≥ 20.19. Downloads the MongoDB binary on first run, caches it after. Source: mongodb-js/devtools-shared.

For local development, mongodb-runner manages a MongoDB binary. Install it once with npm, then start a standalone server or pass -t replset to start a replica set. Transactions require a replica set. The exec subcommand pre-sets MONGODB_URI for any child process, removing the need to manage the URI manually.

Meet Django MongoDB Backend 🎉🎉🎉

  • Built on PyMongo
  • Tracks Django releases: 5.2 6.0
  • A first-class Django database backend
    • Not an ODM bolt-on or sidecar
    • Listed in Django's
      third-party database backends
    • Translates the ORM to MQL
      • str(qs.query) prints MQL
Django MongoDB Backend is a first-class Django database backend built on PyMongo. It tracks Django releases — versions 5.2 and 6.0 are currently supported. It is not an object-document mapper layered on top of Django; it replaces the SQL layer entirely, translating Django's ORM query tree into MongoDB Query Language. As of version 6.0, printing str(qs.query) outputs the resulting aggregation pipeline.

ORM → MQL

As of 6.0, str(qs.query) prints the aggregation pipeline.


>>> qs = (Question.objects
...         .filter(question_text__icontains="mongo")
...         .order_by("-pub_date")[:5])
>>> print(qs.query)
[
  {'$match': {'$expr': {'$regexMatch': {
      'input': '$question_text', 'regex': 'mongo', 'options': 'i'}}}},
  {'$sort': {'pub_date': -1}},
  {'$limit': 5}
]

Each node in Django's query tree gets an as_mql() method (mirroring as_sql()); the compiler walks the tree to build the pipeline. Use qs.explain() for the executed plan.

Each node in Django's internal query tree gains an as_mql() method, mirroring the as_sql() method used by relational backends. The compiler walks this tree to produce an aggregation pipeline. The example translates a filter, sort, and slice into dollar-match, dollar-sort, and dollar-limit stages. Call qs.explain() to retrieve the server's execution plan.

ORM → MQL

Content types & permissions via the Django ORM.


from django.contrib.auth.models import Permission, User
from django.contrib.contenttypes.models import ContentType

# Every installed model has a ContentType row
qs = ContentType.objects.filter(app_label="auth")
str(qs.query)
# [{'$match': {'app_label': {'$eq': 'auth'}}}]

# ContentType for a specific model class
ct = ContentType.objects.get_for_model(User)

# Auth permissions joined to their content type — one query
perms = Permission.objects.select_related("content_type").filter(
    content_type__app_label="auth"
)
The Django content types and permissions framework requires no modification. ContentType.objects.get_for_model, select_related across content type foreign keys, and standard filter calls all translate to MQL automatically. No special handling is required in application code.

ObjectId primary keys

DEFAULT_AUTO_FIELD configures the field used for auto-generated PKs.

BigAutoField

  • 64-bit integer counter
  • Database hands out the next value
  • Awkward under sharding

UUIDField

  • 128-bit random value
  • Generated client-side
  • No time order

ObjectIdAutoField

  • 12-byte BSON ObjectId
  • Timestamp-prefixed — sorts ~chronologically
  • Generated client-side, safe under sharding

ObjectId = 4-byte Unix timestamp · 5-byte random · 3-byte counter (12 bytes total).

Three options exist for auto-generated primary keys. BigAutoField is a 64-bit integer counter issued by the database: straightforward for single-node deployments but problematic under sharding. UUIDField is a 128-bit random value generated client-side with no time ordering. ObjectIdAutoField is a 12-byte BSON ObjectId composed of a 4-byte Unix timestamp prefix, 5 bytes of randomness, and a 3-byte counter. It is generated client-side, sorts approximately chronologically, and is safe under sharding.

Global vs per-app

Set it once in settings.py — or per app in AppConfig.

settings.py


DEFAULT_AUTO_FIELD = \
    "django_mongodb_backend.fields.ObjectIdAutoField"
  • Project-wide default
  • Applies to every app that doesn't override

apps.py


from django.apps import AppConfig


class BlogConfig(AppConfig):
    default_auto_field = "django_mongodb_backend.fields.ObjectIdAutoField"
    name = "blog"
  • Per-app override
  • Wins over the global setting

Model pk > App default_auto_field > DEFAULT_AUTO_FIELD

DEFAULT_AUTO_FIELD in settings.py applies to every app that does not override it. Contrib apps — admin, auth, and contenttypes — default to BigAutoField and require per-app overrides via AppConfig subclasses. The resolution order is: a field declared directly on the model, then the app's default_auto_field, then the project-level DEFAULT_AUTO_FIELD.

The INSTALLED_APPS entries above are defined in your project's apps.py.

Three one-line subclasses — exactly the per-app override pattern from the previous slide.

What the project template does

Action

  • Subclass AuthConfig, AdminConfig, ContentTypesConfig
  • Reconfigure MIGRATION_MODULES to use mongo_migrations.*
  • Add MongoRouter to DATABASE_ROUTERS

Reason

  • Contrib AppConfigs default to BigAutoField; subclassing overrides to ObjectIdAutoField
  • Bundled migrations assume integer primary keys; reconfigured migrations use ObjectIdAutoField
  • Embedded models have no backing collection and must be excluded from routing

The project template includes all three of these changes.

Contrib AppConfigs default to BigAutoField because Django's global default is an integer counter; subclassing overrides that to ObjectIdAutoField. The contrib migrations bundled with Django carry integer primary key assumptions; the reconfigured migration modules replace them with ObjectId-compatible equivalents. MongoRouter prevents the migrate command from targeting embedded models, which exist only as sub-documents within a parent collection and have no corresponding MongoDB collection.

Why MongoDB?

Document model

  • Schema fits the object, not the other way around
  • Nested documents & arrays — no join tables
  • Flexible evolution without painful migrations

Operations

  • Horizontal scale via sharding
  • Replica sets & transactions
  • Atlas: managed, with search & vector search
MongoDB's document model stores related data as nested documents and arrays within a single document, eliminating the need for join tables. The schema reflects the shape of application objects rather than a normalized relational structure. Operationally, MongoDB supports horizontal scaling via sharding, multi-document transactions via replica sets, and managed hosting via Atlas, which adds full-text search and vector search capabilities.

Django on MongoDB?

  • Keep what you love: ORM, admin, migrations, forms, auth
  • Gain document-native modeling: EmbeddedModelField, ArrayField, ObjectIdField
  • Drop into MQL/aggregation when you need it (raw_aggregate)
  • Officially maintained by MongoDB

Repo: github.com/mongodb/django-mongodb-backend

Django MongoDB Backend preserves the complete Django developer experience — ORM, admin, migrations, forms, and authentication — while adding MongoDB-native modeling primitives: EmbeddedModelField, ArrayField, and ObjectIdField. When the ORM abstraction is not sufficient, raw_aggregate provides direct access to the aggregation framework. The backend is officially maintained by MongoDB.

Your first model


from django.db import models


class Movie(models.Model):
    title = models.CharField(max_length=200)
    year = models.IntegerField()
    genres = models.JSONField(default=list)
    runtime = models.IntegerField(null=True)

    class Meta:
        indexes = [models.Index(fields=["year", "title"])]

A standard Django model — no new API to learn. The backend stores each instance as a MongoDB document, and id is automatically a BSON ObjectId rather than an integer.

A model targeting MongoDB is syntactically identical to any Django model. No new API is required. The backend stores each instance as a document in a MongoDB collection. The id field is automatically a BSON ObjectId rather than an integer when ObjectIdAutoField is configured as the default.

Embedded documents


from django_mongodb_backend.fields import EmbeddedModelField
from django_mongodb_backend.models import EmbeddedModel


class Address(EmbeddedModel):
    street = models.CharField(max_length=200)
    city = models.CharField(max_length=100)
    zipcode = models.CharField(max_length=20)


class Customer(models.Model):
    name = models.CharField(max_length=120)
    address = EmbeddedModelField(Address)

Address is stored inside the Customer document — no separate collection, no join. customer.address.city is a plain Python attribute lookup that maps directly to a MongoDB field path.

EmbeddedModel marks a class as a document that lives inside another document rather than in its own collection. EmbeddedModelField declares the embedding on the parent model. Accessing customer.address.city is a plain Python attribute lookup; on the database side it corresponds to the field path address.city within the customer document. No join is performed.

Arrays of embedded docs


from django_mongodb_backend.fields import (
    ArrayField,
    EmbeddedModelArrayField,
)


class LineItem(EmbeddedModel):
    sku = models.CharField(max_length=40)
    qty = models.IntegerField()
    price = models.DecimalField(max_digits=8, decimal_places=2)


class Order(models.Model):
    customer = models.ForeignKey(Customer, on_delete=models.CASCADE)
    items = EmbeddedModelArrayField(LineItem)
    tags = ArrayField(models.CharField(max_length=30), default=list)

Loading an Order fetches its embedded LineItem array and scalar tags in a single document read — no joins, no extra queries.

EmbeddedModelArrayField stores a list of embedded model instances inside the parent document. ArrayField stores a list of scalar values. Loading an Order retrieves its LineItem array and tags list in a single document read. No secondary queries are issued.

Querying


# Top-level fields
Movie.objects.filter(year__gte=2020).order_by("-year")[:10]

# Reach into embedded docs with double-underscore
Customer.objects.filter(address__city="Berlin")

# Array membership
Order.objects.filter(tags__contains=["priority"])

# See the MQL the ORM produced
print(Movie.objects.filter(year=2024).query)
The standard Django queryset API applies without modification. Double-underscore traversal reaches into embedded document subfields: address__city translates to the field path address.city in the generated MQL. The contains lookup on an ArrayField tests for array membership. Printing the query attribute on a queryset displays the MQL pipeline the backend will send to MongoDB.

When you need MQL: raw_aggregate


pipeline = [
    {"$match": {"year": {"$gte": 2020}}},
    {"$group": {"_id": "$year", "count": {"$sum": 1}}},
    {"$sort": {"_id": -1}},
]

qs = Movie.objects.raw_aggregate(pipeline)  # returns a QuerySet
for row in qs:                               # row is a Movie instance
    print(row.year, row.count)               # _id + annotated fields

Full power of the aggregation framework — $lookup, $search, $vectorSearch, …

When the ORM query abstraction is insufficient, raw_aggregate accepts a full MQL aggregation pipeline and returns a queryset whose elements are instances of the model class. Fields computed in the pipeline — such as a count produced by a dollar-group stage — are accessible as attributes on the returned instances. This provides full access to dollar-lookup, dollar-search, dollar-vectorSearch, and any other aggregation operator.

Indexes — including embedded fields


from django_mongodb_backend.indexes import EmbeddedFieldIndex


class Customer(models.Model):
    name = models.CharField(max_length=120)
    address = EmbeddedModelField(Address)

    class Meta:
        indexes = [
            models.Index(fields=["name"]),
            EmbeddedFieldIndex("address.city"),
        ]

New in 6.0.2: index/uniqueness on subfields of embedded & embedded-array fields.

Standard indexes are declared in Meta.indexes using models.Index. Indexes on subfields of embedded documents require EmbeddedFieldIndex, introduced in version 6.0.2. The subfield path is given as a dotted string. Running migrate applies the index to MongoDB.

Unique constraints


from django.db.models import UniqueConstraint
from django_mongodb_backend.constraints import EmbeddedFieldUniqueConstraint


class Customer(models.Model):
    email = models.EmailField(null=True, blank=True)
    address = EmbeddedModelField(Address)

    class Meta:
        constraints = [
            # Multiple NULLs allowed (6.0.2+)
            UniqueConstraint(
                fields=["email"],
                name="uniq_email",
                nulls_distinct=True,
            ),
            EmbeddedFieldUniqueConstraint("address.zipcode"),
        ]

Indexes do the work; the constraint is a thin wrapper over a unique index.

UniqueConstraint on a top-level field generates a unique index in MongoDB. The nulls_distinct option, also introduced in version 6.0.2, permits multiple documents to carry a null value for the constrained field. EmbeddedFieldUniqueConstraint applies the same uniqueness guarantee to a dotted subfield path within an embedded document.

Polymorphic embedded models 6.0.3


from django_mongodb_backend.fields import (
    PolymorphicEmbeddedModelField,
    PolymorphicEmbeddedModelArrayField,
)


class CardPayment(EmbeddedModel):
    last4 = models.CharField(max_length=4)


class WirePayment(EmbeddedModel):
    iban = models.CharField(max_length=34)


class Invoice(models.Model):
    payment = PolymorphicEmbeddedModelField([CardPayment, WirePayment])
    history = PolymorphicEmbeddedModelArrayField([CardPayment, WirePayment])

Indexes & unique constraints on polymorphic subfields are also supported.

PolymorphicEmbeddedModelField and PolymorphicEmbeddedModelArrayField, introduced in version 6.0.3, allow a single field to hold instances of different EmbeddedModel subclasses. The backend writes a type discriminator into the stored document and uses it to deserialize the correct Python class on read. Indexes and unique constraints on polymorphic subfields are supported.

Queryable Encryption 6.0.1

  • Encrypt fields client-side; query them without decrypting server-side
  • Declared on the model, enforced by the backend
  • Migrations refuse to run against a non-encrypted database

from django_mongodb_backend.encryption import EncryptedCharField


class Patient(models.Model):
    name = models.CharField(max_length=120)
    ssn = EncryptedCharField(max_length=11, queries={"queryType": "equality"})
MongoDB Queryable Encryption, available since version 6.0.1, encrypts field values on the client before transmission. The server stores and processes only ciphertext; plaintext is never exposed server-side. Equality queries on encrypted fields function without server-side decryption. Declaring EncryptedCharField is the only change required in application code. The backend enforces that encrypted collections are created via migrate before any write is attempted, preventing accidental creation of unencrypted collections.

Spatial lookups 6.0.1


from django.contrib.gis.geos import Point
from django.contrib.gis.measure import D

# 2dsphere index under the hood
Cafe.objects.filter(
    location__dwithin=(Point(13.405, 52.52), D(km=2)),

GeoDjango-style queries, MongoDB-native execution.

Spatial lookups, available since version 6.0.1, follow the GeoDjango API. The dwithin lookup accepts a Point and a Distance object and translates to a 2dsphere index query in MongoDB. No PostGIS installation or separate spatial database is required.

Limitations

  • No SQL — some third-party apps that emit raw SQL won't work
  • Cross-collection joins exist, but you'll lean on embedding
  • contrib.gis support is partial (lookups, not full GeoDjango)
  • Schema migrations are lighter — MongoDB doesn't enforce a fixed shape

Check the docs' "Known issues" page before porting a large app.

Four limitations are worth noting. The backend does not execute SQL; third-party packages that emit raw SQL will not function. Cross-collection joins are available via the dollar-lookup aggregation operator, but the document model favors embedding over joining. The contrib.gis integration supports lookups but not the full GeoDjango feature set. Finally, because MongoDB does not enforce a fixed document shape, schema migrations are lighter — adding or removing a field does not require altering existing documents.

The polls application is the Django tutorial project ported to Django MongoDB Backend. polls/models.py


from django.db import models
from django_mongodb_backend.fields import ArrayField, EmbeddedModelArrayField
from django_mongodb_backend.indexes import SearchIndex
from django_mongodb_backend.managers import MongoManager
from django_mongodb_backend.models import EmbeddedModel


class Choice(EmbeddedModel):
    choice_text = models.CharField(max_length=200)
    votes = models.IntegerField(default=0)


class Question(models.Model):
    question_text = models.CharField(max_length=200)
    pub_date = models.DateTimeField("date published")
    choices = EmbeddedModelArrayField(Choice, blank=True, default=list)
    tags = ArrayField(models.CharField(max_length=50), blank=True, default=list)

    objects = MongoManager()

    class Meta:
        indexes = [
            SearchIndex(
                name="polls_question_search",
                field_mappings={
                    "question_text": {"type": "string"},
                    "tags": {"type": "string"},
                },
            ),
        ]

One collection, one document per question — choices and tags live inside.

Choice is an EmbeddedModel — it has no separate collection. Question is a standard model with choices stored as an EmbeddedModelArrayField and tags as an ArrayField. MongoManager is assigned to objects to expose raw_aggregate. The SearchIndex in Meta defines the Atlas Search index used by the search view.

Voting on an embedded Choice


def vote(request, pk):
    question = get_object_or_404(Question, pk=pk)
    try:
        index = int(request.POST["choice"])
        choice = question.choices[index]
    except (KeyError, ValueError, IndexError):
        return HttpResponseRedirect(reverse("polls:detail", args=(question.pk,)))
    choice.votes = (choice.votes or 0) + 1
    question.choices[index] = choice
    question.save()
    return HttpResponseRedirect(reverse("polls:results", args=(question.pk,)))

Mutate the embedded Choice in place, reassign it, save the parent.

To increment a vote count, the view retrieves the Question, reads the Choice at the submitted index, increments its votes attribute, writes the modified Choice back into the list, and calls save() on the Question. The entire operation is a single document write.

raw_aggregate in a view


class AnalyticsView(TemplateView):
    template_name = "polls/analytics.html"

    def get_context_data(self, **kwargs):
        ctx = super().get_context_data(**kwargs)
        pipeline = [
            {"$project": {
                "question_text": 1, "pub_date": 1, "choices": 1, "tags": 1,
                "year":  {"$year": "$pub_date"},
                "votes": {"$sum": "$choices.votes"},
            }},
            {"$sort": {"pub_date": -1}},
        ]
        questions = list(Question.objects.raw_aggregate(pipeline))
        per_year = {}
        for q in questions:
            per_year.setdefault(q.year, 0)
            per_year[q.year] += q.votes
        ctx["questions"] = questions
        ctx["per_year"] = sorted(per_year.items())
        return ctx

$sum: "$choices.votes" sums across the embedded array — no extra queries.

AnalyticsView passes a pipeline to raw_aggregate. The dollar-project stage computes year from pub_date and sums the votes field across the embedded choices array using dollar-sum. The returned queryset yields Question instances with year and votes accessible as attributes. No additional queries are issued to compute the per-year totals.

Atlas Search with a fallback


class SearchView(TemplateView):
    template_name = "polls/search.html"

    def get_context_data(self, **kwargs):
        ctx = super().get_context_data(**kwargs)
        q = (self.request.GET.get("q") or "").strip()
        ctx["q"], ctx["results"], ctx["mode"] = q, [], "none"
        if not q:
            return ctx
        try:
            from django_mongodb_backend.expressions.search import SearchText
            ctx["results"] = list(
                Question.objects.annotate(_search=SearchText("polls_question_search", q))
            )
            ctx["mode"] = "atlas"
        except Exception:
            ctx["results"] = list(Question.objects.filter(question_text__icontains=q))
            ctx["mode"] = "fallback"
        return ctx

Atlas: $search. Local replica set: __icontains + a banner.

SearchView attempts Atlas Search using SearchText, which generates a dollar-search aggregation stage. If that raises an exception — for example, because the Atlas Search index does not exist on a local replica set — the except block falls back to an icontains filter. The mode variable in the context indicates to the template which code path was taken.
