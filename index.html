Meet Django MongoDB Backend

  • A first-class Django database backend (not an ODM bolt-on)
  • Tracks Django releases: 5.2 6.0
  • Built on PyMongo
  • Translates the ORM to MQL — str(qs.query) prints MQL
This is the framing slide. django-mongodb-backend is a Django database backend — the same plug point as the postgres, mysql, sqlite backends. It is NOT an ODM layered on top of an ORM. That distinction matters, because it means querysets, the admin, migrations, and third-party apps that go through the ORM all just work. It tracks Django releases — 5.2 and 6.0 — so you pin the matching major. It's built on PyMongo, so anything you already know about driver connection pooling and BSON applies. And here's a fun party trick: str(qs.query) on any queryset prints the MQL the backend produced. Useful for debugging and for learning how the translation works.

Install


# Pick the series matching your Django version
pip install "django-mongodb-backend==6.0.*"

# Start a project from MongoDB's template
django-admin startproject mysite \
  --template https://github.com/mongodb-labs/django-mongodb-project/archive/refs/heads/6.0.x.zip

The project template wires up DATABASES, DEFAULT_AUTO_FIELD, and migration helpers for you.

Two commands and you're moving. Pip install with a version pin that matches your Django series — 6.0.* tracks Django 6.0. Then the project template: django-admin startproject pointing at MongoDB's template repository on GitHub. The template isn't strictly required, but it saves you ten minutes of fiddling — it pre-fills DATABASES with your connection string, sets DEFAULT_AUTO_FIELD to ObjectId, and patches a couple of migration helpers. If you're starting a new project, just use it.

settings.py


import os

DATABASES = {
    "default": {
        "ENGINE": "django_mongodb_backend",
        "HOST": os.environ.get("MONGODB_URI", "mongodb://localhost:27017"),
        "NAME": "mysite",
    },
}

# Use ObjectId as the default primary key
DEFAULT_AUTO_FIELD = "django_mongodb_backend.fields.ObjectIdAutoField"

INSTALLED_APPS = [
    # ...
    "django_mongodb_backend",
]

HOST accepts any MongoDB connection string — including Atlas SRV URIs and TLS options. Read it from the environment so secrets stay out of the repo.

Three things to call out. HOST takes the connection string directly — any MongoDB URI, including Atlas SRV URIs with TLS options, goes straight into HOST. We read it from the MONGODB_URI environment variable so credentials never live in the repo. No helper needed, no hand-mapping HOST, PORT, NAME, OPTIONS. (If you've used earlier 5.x docs you might remember a parse_uri() helper — that was deprecated in 5.2.1 and removed in 6.0.) DEFAULT_AUTO_FIELD pointing at ObjectIdAutoField means every model's primary key is a real BSON ObjectId, not an integer, not a UUID. That matters at scale and in distributed writes. And adding django_mongodb_backend to INSTALLED_APPS registers the backend's system checks, management commands, and admin URL converter.

ObjectId primary keys

DEFAULT_AUTO_FIELD picks the field for auto-generated PKs — "auto" means generated, not incremented.

BigAutoField

  • 64-bit integer counter
  • Database hands out the next value
  • Awkward under sharding

UUIDField

  • 128-bit random value
  • Generated client-side
  • No time order

ObjectIdAutoField

  • 12-byte BSON ObjectId
  • Timestamp-prefixed — sorts ~chronologically
  • Generated client-side, safe under sharding

ObjectId = 4-byte Unix timestamp · 5-byte random · 3-byte counter (12 bytes total).

Quick callback to DEFAULT_AUTO_FIELD on the previous slide. "Auto" here means auto-generated — not auto-incrementing. Three common options. BigAutoField is a 64-bit integer counter the database hands out — fine on one server, contention under sharding. UUIDField is 128 random bits generated client-side — no central coordination, but no time order either, so "newest first" scans can't ride the primary key. On MongoDB you get an ObjectId — 12 bytes generated client-side by the driver. The first 4 bytes are a Unix timestamp, so two ObjectIds made a second apart still sort by time. No central counter to coordinate, so sharded writes scale cleanly. And it's the native _id type on the wire — what mongosh prints, what change streams emit, what the admin uses for object URLs.

Global vs per-app

Set it once in settings.py — or per app in AppConfig.

settings.py


DEFAULT_AUTO_FIELD = "django_mongodb_backend.fields.ObjectIdAutoField"
  • Project-wide default
  • Applies to every app that doesn't override

apps.py


from django.apps import AppConfig


class BlogConfig(AppConfig):
    default_auto_field = "django_mongodb_backend.fields.ObjectIdAutoField"
    name = "blog"
  • Per-app override
  • Wins over the global setting

Precedence: model pk > app default_auto_field > DEFAULT_AUTO_FIELD.

Two places to configure this. The global DEFAULT_AUTO_FIELD in settings.py is the project-wide default — every app that doesn't say otherwise picks it up. The per-app default_auto_field on AppConfig is an override for one app, and it wins over the global setting. Why does the per-app knob exist? Django's contrib apps — auth, admin, contenttypes — ship their own AppConfigs that pin default_auto_field to BigAutoField for backwards compatibility. The django-mongodb-project template you saw earlier handles this for you by subclassing those AppConfigs and pointing them at ObjectIdAutoField, so every table in the project ends up with an ObjectId PK. Precedence order, top-down: an explicit primary_key=True field on the model wins; otherwise the app's default_auto_field; otherwise the global DEFAULT_AUTO_FIELD.

Why MongoDB?

Document model

  • Schema fits the object, not the other way around
  • Nested documents & arrays — no join tables
  • Flexible evolution without painful migrations

Operations

  • Horizontal scale via sharding
  • Replica sets & transactions
  • Atlas: managed, with search & vector search
Two angles to motivate this. On the left: the document model. Your schema fits the object instead of the object fitting the schema. A customer has an address; the address rides along inside the customer document. Adding a country field tomorrow doesn't require a migration on millions of rows. On the right: operations. Sharding for horizontal scale, replica sets for high availability, ACID transactions when you need them, and Atlas if you'd rather not run it yourself — including full-text search and vector search as first-class features.

Django on MongoDB?

  • Keep what you love: ORM, admin, migrations, forms, auth
  • Gain document-native modeling: EmbeddedModelField, ArrayField, ObjectIdField
  • Drop into MQL/aggregation when you need it (raw_aggregate)
  • Officially maintained by MongoDB

Repo: github.com/mongodb/django-mongodb-backend

The pitch in four bullets. You don't give up Django — admin, migrations, forms, auth, signals, the whole stack keeps working. What you gain is document-native modeling: EmbeddedModelField, ArrayField, ObjectIdField. When the ORM doesn't reach far enough — full-text search, complex aggregations, $lookup — raw_aggregate lets you drop in any MQL pipeline and get model instances back. And critically: this is officially maintained by MongoDB. Not a hobby project, not a community fork that might bitrot. There's a team behind it.

Your first model


from django.db import models


class Movie(models.Model):
    title = models.CharField(max_length=200)
    year = models.IntegerField()
    genres = models.JSONField(default=list)
    runtime = models.IntegerField(null=True)

    class Meta:
        indexes = [models.Index(fields=["year", "title"])]

Looks like Django, stores like MongoDB. id is an ObjectId.

This is just a Django model. Nothing exotic. CharField, IntegerField, JSONField for the genres list, a compound Index on (year, title). If you've written a Django model before, you've written this slide. The only invisible difference: id is an ObjectId instead of an AutoField integer, because of DEFAULT_AUTO_FIELD. On disk this is one document in a `movies` collection — no separate tables for the index, no separate table for the JSON list. One collection, one document per movie.

Embedded documents


from django_mongodb_backend.fields import EmbeddedModelField
from django_mongodb_backend.models import EmbeddedModel


class Address(EmbeddedModel):
    street = models.CharField(max_length=200)
    city = models.CharField(max_length=100)
    zip = models.CharField(max_length=20)


class Customer(models.Model):
    name = models.CharField(max_length=120)
    address = EmbeddedModelField(Address)

One document. No join. customer.address.city just works.

Now we leave SQL-land. EmbeddedModel is a model class that doesn't have its own collection — it can only exist embedded inside another model. Address goes inside Customer via EmbeddedModelField. The whole thing is one document on disk. No join, no foreign key, no migration to add a column to the address. customer.address.city is both a Python attribute lookup and a single MongoDB field path. This is the move that maps most "has-one" relationships in your domain to a single round-trip read.

Arrays of embedded docs


from django_mongodb_backend.fields import (
    ArrayField,
    EmbeddedModelArrayField,
)


class LineItem(EmbeddedModel):
    sku = models.CharField(max_length=40)
    qty = models.IntegerField()
    price = models.DecimalField(max_digits=8, decimal_places=2)


class Order(models.Model):
    customer = models.ForeignKey(Customer, on_delete=models.CASCADE)
    items = EmbeddedModelArrayField(LineItem)
    tags = ArrayField(models.CharField(max_length=30), default=list)

One round-trip. The whole order — line items, tags — hydrated together.

Same idea, repeated. Order has many LineItems — instead of an order_items table with a foreign key back to orders, you get an array of LineItem subdocuments stored on the Order itself. One round-trip loads the entire order with all its lines. ArrayField is the simpler cousin: an array of plain scalar values — CharField in this case, for tags. Use ArrayField for "list of strings", EmbeddedModelArrayField for "list of structured records". This is the modeling decision that makes most ported Django apps feel faster on MongoDB than they did on Postgres.

Querying feels like Django


# Top-level fields
Movie.objects.filter(year__gte=2020).order_by("-year")[:10]

# Reach into embedded docs with double-underscore
Customer.objects.filter(address__city="Berlin")

# Array membership
Order.objects.filter(tags__contains=["priority"])

# See the MQL the ORM produced
print(Movie.objects.filter(year=2024).query)
Identical to the ORM you already know. filter, gte, order_by, slicing — same syntax, same chaining. Reaching into embedded documents is just double-underscore traversal: address__city. Array membership uses __contains. The last line is the debug trick. On a Postgres backend, str(qs.query) prints the SQL. On this backend, it prints the MQL — the actual $match/$project the backend will send. Great for ticket reports, great for understanding what the ORM did with your filter.

When you need MQL: raw_aggregate


pipeline = [
    {"$match": {"year": {"$gte": 2020}}},
    {"$group": {"_id": "$year", "count": {"$sum": 1}}},
    {"$sort": {"_id": -1}},
]

for row in Movie.objects.raw_aggregate(pipeline):
    print(row)

Full power of the aggregation framework — $lookup, $search, $vectorSearch, …

When the ORM doesn't reach far enough — and sometimes it doesn't — raw_aggregate is the escape hatch. You hand it a real MongoDB aggregation pipeline as a list of stage dicts; the backend runs it and hydrates the output documents back into model instances. That gives you the entire aggregation framework: $lookup for cross-collection joins, $search for Atlas Search full-text, $vectorSearch for nearest-neighbor on embeddings. None of that requires dropping back to PyMongo or maintaining a parallel data access layer.

Indexes — including embedded fields


from django_mongodb_backend.indexes import EmbeddedFieldIndex


class Customer(models.Model):
    name = models.CharField(max_length=120)
    address = EmbeddedModelField(Address)

    class Meta:
        indexes = [
            models.Index(fields=["name"]),
            EmbeddedFieldIndex("address.city"),
        ]

New in 6.0.2: index/uniqueness on subfields of embedded & embedded-array fields.

Standard Django Index, on top-level fields, works exactly as you'd expect. The new piece is EmbeddedFieldIndex — it lets you index a subfield of an embedded document. Here, address.city. Under the hood, MongoDB creates a normal index on the dotted path. Any query that filters or sorts on customer.address__city will use it. This shipped in 6.0.2 and was a notable gap before that — without it, embedded documents were hard to use for hot query paths.

Unique constraints, the Mongo way


from django.db.models import UniqueConstraint
from django_mongodb_backend.constraints import EmbeddedFieldUniqueConstraint


class Customer(models.Model):
    email = models.EmailField(null=True, blank=True)
    address = EmbeddedModelField(Address)

    class Meta:
        constraints = [
            # Multiple NULLs allowed (6.0.2+)
            UniqueConstraint(
                fields=["email"],
                name="uniq_email",
                nulls_distinct=True,
            ),
            EmbeddedFieldUniqueConstraint("address.zip"),
        ]

Indexes do the work; the constraint is a thin wrapper over a unique index.

Two flavors of unique. Django's UniqueConstraint with nulls_distinct=True — that means multiple rows with NULL email are all allowed; only non-null values are deduped. This is the same semantics Postgres got in Django 5.0, and it's available in this backend as of 6.0.2. EmbeddedFieldUniqueConstraint is the embedded counterpart of EmbeddedFieldIndex from the previous slide — uniqueness on a subfield, here address.zip. Same dotted-path mechanism, enforced by a unique index on the collection.

Polymorphic embedded models 6.0.3


from django_mongodb_backend.fields import (
    PolymorphicEmbeddedModelField,
    PolymorphicEmbeddedModelArrayField,
)


class CardPayment(EmbeddedModel):
    last4 = models.CharField(max_length=4)


class WirePayment(EmbeddedModel):
    iban = models.CharField(max_length=34)


class Invoice(models.Model):
    payment = PolymorphicEmbeddedModelField([CardPayment, WirePayment])
    history = PolymorphicEmbeddedModelArrayField([CardPayment, WirePayment])

Indexes & unique constraints on polymorphic subfields are also supported.

New in 6.0.3, and it's the feature I get the most questions about. Polymorphic embedded fields: an embedded field whose type can be one of several model classes. Here, Invoice.payment is either a CardPayment or a WirePayment. The backend stores a class discriminator alongside the data, and on read it reconstructs the right model class — so invoice.payment is a CardPayment instance with a real .last4 attribute, or a WirePayment with .iban. PolymorphicEmbeddedModelArrayField is the array variant, for things like a payment history with mixed types. Indexes and unique constraints work on the subfields the same way.

Queryable Encryption 6.0.1

  • Encrypt fields client-side; query them without decrypting server-side
  • Declared on the model, enforced by the backend
  • Migrations refuse to run against a non-encrypted database

from django_mongodb_backend.encryption import EncryptedCharField


class Patient(models.Model):
    name = models.CharField(max_length=120)
    ssn = EncryptedCharField(max_length=11, queries={"queryType": "equality"})
Queryable Encryption is a MongoDB-level feature: fields are encrypted client-side, the server only ever sees ciphertext, but you can still do equality queries on them — because the encryption is structured in a way that lets the server match without decrypting. In Django, you declare it on the model: EncryptedCharField with the query type you want — equality here. The backend has a guardrail: migrations refuse to run against a non-encrypted database, so you can't accidentally write plaintext PII into a dev environment that wasn't set up for it. Use case: SSNs, account numbers, anything regulated.

Spatial lookups 6.0.1


from django.contrib.gis.geos import Point
from django.contrib.gis.measure import D

# 2dsphere index under the hood
Cafe.objects.filter(
    location__dwithin=(Point(13.405, 52.52), D(km=2)),
)

GeoDjango-style queries, MongoDB-native execution.

GeoDjango-style queries, executed natively on a MongoDB 2dsphere index. Cafe.objects.filter with location__dwithin, passing a Point and a Distance — same API you'd use against PostGIS. Under the hood, the backend translates that to $geoNear or $geoWithin depending on the lookup. The contrib.gis support is partial — see the limitations slide a few ahead — but the lookups people reach for most often are there: dwithin, intersects, within, contains.

The Django admin… still works

  • Register models exactly as you always have
  • Embedded fields render as nested forms
  • ObjectId primary keys are matched in URLs out of the box 6.0.3

# urls.py
urlpatterns = [
    path("orders/<objectid:pk>/", OrderDetail.as_view()),
]
The "still works" is half-joke, half-relief. Django admin is one of the things people are afraid they'll lose when switching backends — you don't. Register your models the way you always have. Embedded fields render as inline nested forms automatically, because the field knows how to render itself. As of 6.0.3, the URL path converter for ObjectId is registered for you — you can write <objectid:pk> directly in your urlconf and the lookup just works. Before that, you'd write a custom converter. Now you don't.

Honest limitations

  • No SQL — some third-party apps that emit raw SQL won't work
  • Cross-collection joins exist, but you'll lean on embedding
  • contrib.gis support is partial (lookups, not full GeoDjango)
  • Schema migrations are lighter — MongoDB doesn't enforce a fixed shape

Check the docs' "Known issues" page before porting a large app.

Be honest with the room. Things that won't work: any third-party Django app that emits raw SQL — no shim is going to translate that in general, and you'll find out quickly when you exercise the feature. Cross-collection joins exist via $lookup, but the document philosophy says embed first; if you find yourself joining a lot, your data model is fighting MongoDB's strengths. contrib.gis is partial — lookups but not the full GeoDjango feature set. And schema migrations exist but are lighter, because MongoDB doesn't enforce a fixed shape — a migration is mostly index DDL and data backfills, not column add/drop. Always read the docs' "Known issues" page before porting a large existing app.
