# Run a command with MONGODB_URI pre-set

Requires Node.js ≥ 20.19. Downloads the MongoDB binary on first run, caches it after. Source: mongodb-js/devtools-shared.

mongodb-runner is the fastest local MongoDB — npm install once, then start/stop/exec. Use -t replset for transactions. The exec subcommand sets MONGODB_URI in the environment before running your command, making CI one-liners trivial.

Meet Django MongoDB Backend 🎉🎉🎉

  • Built on PyMongo
  • Tracks Django releases: 5.2 6.0
  • A first-class Django database backend
    • Not an ODM bolt-on or sidecar
    • Listed in Django's
      third-party database backends
    • Translates the ORM to MQL
      • str(qs.query) prints MQL
Key distinction: this is a Django database backend — the same plug point as postgres or sqlite — not an ODM bolt-on. The ORM, admin, migrations, and third-party apps that go through the ORM all just work.

ORM → MQL

As of 6.0, str(qs.query) prints the aggregation pipeline.


>>> qs = (Question.objects
...         .filter(question_text__icontains="mongo")
...         .order_by("-pub_date")[:5])
>>> print(qs.query)
[
  {'$match': {'$expr': {'$regexMatch': {
      'input': '$question_text', 'regex': 'mongo', 'options': 'i'}}}},
  {'$sort': {'pub_date': -1}},
  {'$limit': 5}
]

Each node in Django's query tree gets an as_mql() method (mirroring as_sql()); the compiler walks the tree to build the pipeline. Use qs.explain() for the executed plan.

str(qs.query) prints the actual MQL pipeline — icontains → $regexMatch, order_by → $sort, slicing → $limit. New in 6.0. Use qs.explain() for the executed plan with index stats.

ORM → MQL

Content types & permissions via the Django ORM.


from django.contrib.auth.models import Permission, User
from django.contrib.contenttypes.models import ContentType

# Every installed model has a ContentType row
qs = ContentType.objects.filter(app_label="auth")
str(qs.query)
# [{'$match': {'app_label': {'$eq': 'auth'}}}]

# ContentType for a specific model class
ct = ContentType.objects.get_for_model(User)

# Auth permissions joined to their content type — one query
perms = Permission.objects.select_related("content_type").filter(
    content_type__app_label="auth"
)
ContentType and Permission are standard Django ORM models — they work identically against MongoDB. select_related across collections becomes a $lookup stage; no special handling needed.

ObjectId primary keys

DEFAULT_AUTO_FIELD configures the field used for auto-generated PKs.

BigAutoField

  • 64-bit integer counter
  • Database hands out the next value
  • Awkward under sharding

UUIDField

  • 128-bit random value
  • Generated client-side
  • No time order

ObjectIdAutoField

  • 12-byte BSON ObjectId
  • Timestamp-prefixed — sorts ~chronologically
  • Generated client-side, safe under sharding

ObjectId = 4-byte Unix timestamp · 5-byte random · 3-byte counter (12 bytes total).

ObjectId is 12 bytes, timestamp-prefixed, generated client-side — sorts ~chronologically, scales cleanly under sharding, and is MongoDB's native _id type on the wire.

Global vs per-app

Set it once in settings.py — or per app in AppConfig.

settings.py


DEFAULT_AUTO_FIELD = \
    "django_mongodb_backend.fields.ObjectIdAutoField"
  • Project-wide default
  • Applies to every app that doesn't override

apps.py


from django.apps import AppConfig


class BlogConfig(AppConfig):
    default_auto_field = "django_mongodb_backend.fields.ObjectIdAutoField"
    name = "blog"
  • Per-app override
  • Wins over the global setting

Model pk > App default_auto_field > DEFAULT_AUTO_FIELD

Precedence: model pk field > app default_auto_field > global DEFAULT_AUTO_FIELD. Contrib apps (auth, admin, contenttypes) default to BigAutoField — the project template subclasses their AppConfigs to override this.

The contrib AppConfigs

The INSTALLED_APPS entries above are defined in your project's apps.py.

from django.contrib.auth.apps import AuthConfig
from django.contrib.contenttypes.apps import ContentTypesConfig


class MongoAdminConfig(AdminConfig):
    default_auto_field = "django_mongodb_backend.fields.ObjectIdAutoField"


class MongoAuthConfig(AuthConfig):
    default_auto_field = "django_mongodb_backend.fields.ObjectIdAutoField"


class MongoContentTypesConfig(ContentTypesConfig):
    default_auto_field = "django_mongodb_backend.fields.ObjectIdAutoField"

Three one-line subclasses — exactly the per-app override pattern from the previous slide.

Three one-line subclasses — each overrides default_auto_field to ObjectIdAutoField. This is Django's documented escape hatch; editing contrib apps directly would break backwards compatibility.

What the project template does

Action

  • Subclass AuthConfig, AdminConfig, ContentTypesConfig
  • Reconfigure MIGRATION_MODULES to use mongo_migrations.*
  • Add MongoRouter to DATABASE_ROUTERS

Reason

  • Contrib AppConfigs default to BigAutoField; subclassing overrides to ObjectIdAutoField
  • Bundled migrations assume integer primary keys; reconfigured migrations use ObjectIdAutoField
  • Embedded models have no backing collection and must be excluded from routing

The project template includes all three of these changes.

Summary: subclass AppConfigs → ObjectId PKs; redirect MIGRATION_MODULES → ObjectId-friendly migrations; add MongoRouter → embedded models excluded from migrate.

Why MongoDB?

Document model

  • Schema fits the object, not the other way around
  • Nested documents & arrays — no join tables
  • Flexible evolution without painful migrations

Operations

  • Horizontal scale via sharding
  • Replica sets & transactions
  • Atlas: managed, with search & vector search
Document model: schema fits the object, not vice versa — nested data without join tables, flexible evolution. Operations: sharding, replica sets, ACID transactions, and Atlas managed search + vector search.

Django on MongoDB?

  • Keep what you love: ORM, admin, migrations, forms, auth
  • Gain document-native modeling: EmbeddedModelField, ArrayField, ObjectIdField
  • Drop into MQL/aggregation when you need it (raw_aggregate)
  • Officially maintained by MongoDB

Repo: github.com/mongodb/django-mongodb-backend

You keep everything you love about Django and gain document-native modeling (EmbeddedModelField, ArrayField, ObjectIdField) plus raw_aggregate for full MQL power. Officially maintained by MongoDB.

Your first model


from django.db import models


class Movie(models.Model):
    title = models.CharField(max_length=200)
    year = models.IntegerField()
    genres = models.JSONField(default=list)
    runtime = models.IntegerField(null=True)

    class Meta:
        indexes = [models.Index(fields=["year", "title"])]

A standard Django model — no new API to learn. The backend stores each instance as a MongoDB document, and id is automatically a BSON ObjectId rather than an integer.

A standard Django model — nothing new to learn. The only invisible difference: id is an ObjectId, not an integer, because of DEFAULT_AUTO_FIELD. One document per movie, one collection on disk.

Embedded documents


from django_mongodb_backend.fields import EmbeddedModelField
from django_mongodb_backend.models import EmbeddedModel


class Address(EmbeddedModel):
    street = models.CharField(max_length=200)
    city = models.CharField(max_length=100)
    zip = models.CharField(max_length=20)


class Customer(models.Model):
    name = models.CharField(max_length=120)
    address = EmbeddedModelField(Address)

Address is stored inside the Customer document — no separate collection, no join. customer.address.city is a plain Python attribute lookup that maps directly to a MongoDB field path.

EmbeddedModel has no backing collection — it lives inside its parent. Address is stored inside the Customer document; customer.address.city is one Python attribute lookup and one MongoDB field path. No joins, no extra queries.

Arrays of embedded docs


from django_mongodb_backend.fields import (
    ArrayField,
    EmbeddedModelArrayField,
)


class LineItem(EmbeddedModel):
    sku = models.CharField(max_length=40)
    qty = models.IntegerField()
    price = models.DecimalField(max_digits=8, decimal_places=2)


class Order(models.Model):
    customer = models.ForeignKey(Customer, on_delete=models.CASCADE)
    items = EmbeddedModelArrayField(LineItem)
    tags = ArrayField(models.CharField(max_length=30), default=list)

Loading an Order fetches its embedded LineItem array and scalar tags in a single document read — no joins, no extra queries.

EmbeddedModelArrayField: array of structured subdocuments (LineItem). ArrayField: array of scalars (tags). One document read loads the entire Order — no join to an order_items table.

When you need MQL: raw_aggregate


pipeline = [
    {"$match": {"year": {"$gte": 2020}}},
    {"$group": {"_id": "$year", "count": {"$sum": 1}}},
    {"$sort": {"_id": -1}},
]

qs = Movie.objects.raw_aggregate(pipeline)  # returns a QuerySet
for row in qs:                               # row is a Movie instance
    print(row.year, row.count)               # _id + annotated fields

Full power of the aggregation framework — $lookup, $search, $vectorSearch, …

raw_aggregate hands a full MQL pipeline to the backend and returns model instances. Full aggregation framework available — $lookup, $search, $vectorSearch — without dropping to PyMongo.

Indexes — including embedded fields


from django_mongodb_backend.indexes import EmbeddedFieldIndex


class Customer(models.Model):
    name = models.CharField(max_length=120)
    address = EmbeddedModelField(Address)

    class Meta:
        indexes = [
            models.Index(fields=["name"]),
            EmbeddedFieldIndex("address.city"),
        ]

New in 6.0.2: index/uniqueness on subfields of embedded & embedded-array fields.

EmbeddedFieldIndex (new in 6.0.2) indexes a dotted subfield path. Any filter or sort on address__city will use it — previously a notable gap for hot query paths on embedded docs.

Unique constraints


from django.db.models import UniqueConstraint
from django_mongodb_backend.constraints import EmbeddedFieldUniqueConstraint


class Customer(models.Model):
    email = models.EmailField(null=True, blank=True)
    address = EmbeddedModelField(Address)

    class Meta:
        constraints = [
            # Multiple NULLs allowed (6.0.2+)
            UniqueConstraint(
                fields=["email"],
                name="uniq_email",
                nulls_distinct=True,
            ),
            EmbeddedFieldUniqueConstraint("address.zip"),
        ]

Indexes do the work; the constraint is a thin wrapper over a unique index.

nulls_distinct=True allows multiple NULL emails while deduping non-nulls. EmbeddedFieldUniqueConstraint enforces uniqueness on an embedded subfield (address.zip) via a unique index on the dotted path.

Polymorphic embedded models 6.0.3


from django_mongodb_backend.fields import (
    PolymorphicEmbeddedModelField,
    PolymorphicEmbeddedModelArrayField,
)


class CardPayment(EmbeddedModel):
    last4 = models.CharField(max_length=4)


class WirePayment(EmbeddedModel):
    iban = models.CharField(max_length=34)


class Invoice(models.Model):
    payment = PolymorphicEmbeddedModelField([CardPayment, WirePayment])
    history = PolymorphicEmbeddedModelArrayField([CardPayment, WirePayment])

Indexes & unique constraints on polymorphic subfields are also supported.

New in 6.0.3. A polymorphic embedded field stores a class discriminator alongside the data; on read the backend reconstructs the correct model class — CardPayment with .last4 or WirePayment with .iban.

Queryable Encryption 6.0.1

  • Encrypt fields client-side; query them without decrypting server-side
  • Declared on the model, enforced by the backend
  • Migrations refuse to run against a non-encrypted database

from django_mongodb_backend.encryption import EncryptedCharField


class Patient(models.Model):
    name = models.CharField(max_length=120)
    ssn = EncryptedCharField(max_length=11, queries={"queryType": "equality"})
Fields are encrypted client-side; the server only ever sees ciphertext, yet equality queries still work. Declare it on the model with EncryptedCharField. Migrations refuse to run against a non-encrypted database — a built-in guardrail.

Limitations

  • No SQL — some third-party apps that emit raw SQL won't work
  • Cross-collection joins exist, but you'll lean on embedding
  • contrib.gis support is partial (lookups, not full GeoDjango)
  • Schema migrations are lighter — MongoDB doesn't enforce a fixed shape

Check the docs' "Known issues" page before porting a large app.

Third-party apps that emit raw SQL won't work. Embed first — heavy $lookup usage fights MongoDB's strengths. contrib.gis is partial. Check the docs' "Known issues" page before porting a large app.

The Django tutorial polls app ported to django-mongodb-backend — covers embedded models, ArrayField, raw_aggregate, and Atlas Search with a local fallback.

polls/models.py


from django.db import models
from django_mongodb_backend.fields import ArrayField, EmbeddedModelArrayField
from django_mongodb_backend.indexes import SearchIndex
from django_mongodb_backend.managers import MongoManager
from django_mongodb_backend.models import EmbeddedModel


class Choice(EmbeddedModel):
    choice_text = models.CharField(max_length=200)
    votes = models.IntegerField(default=0)


class Question(models.Model):
    question_text = models.CharField(max_length=200)
    pub_date = models.DateTimeField("date published")
    choices = EmbeddedModelArrayField(Choice, blank=True, default=list)
    tags = ArrayField(models.CharField(max_length=50), blank=True, default=list)

    objects = MongoManager()

    class Meta:
        indexes = [
            SearchIndex(
                name="polls_question_search",
                field_mappings={
                    "question_text": {"type": "string"},
                    "tags": {"type": "string"},
                },
            ),
        ]

One collection, one document per question — choices and tags live inside.

Three MongoDB-specific things: Choice as EmbeddedModel, choices as EmbeddedModelArrayField, tags as ArrayField of strings. MongoManager unlocks raw_aggregate; SearchIndex declares the Atlas Search index.

Voting on an embedded Choice


def vote(request, pk):
    question = get_object_or_404(Question, pk=pk)
    try:
        index = int(request.POST["choice"])
        choice = question.choices[index]
    except (KeyError, ValueError, IndexError):
        return HttpResponseRedirect(reverse("polls:detail", args=(question.pk,)))
    choice.votes = (choice.votes or 0) + 1
    question.choices[index] = choice
    question.save()
    return HttpResponseRedirect(reverse("polls:results", args=(question.pk,)))

Mutate the embedded Choice in place, reassign it, save the parent.

Mutate the embedded Choice, reassign it in the array, save the Question — one round-trip, no second collection. The form uses list index to identify the choice, so don't reorder between GET and POST.

raw_aggregate in a view


class AnalyticsView(TemplateView):
    template_name = "polls/analytics.html"

    def get_context_data(self, **kwargs):
        ctx = super().get_context_data(**kwargs)
        pipeline = [
            {"$project": {
                "question_text": 1, "pub_date": 1, "choices": 1, "tags": 1,
                "year":  {"$year": "$pub_date"},
                "votes": {"$sum": "$choices.votes"},
            }},
            {"$sort": {"pub_date": -1}},
        ]
        questions = list(Question.objects.raw_aggregate(pipeline))
        per_year = {}
        for q in questions:
            per_year.setdefault(q.year, 0)
            per_year[q.year] += q.votes
        ctx["questions"] = questions
        ctx["per_year"] = sorted(per_year.items())
        return ctx

$sum: "$choices.votes" sums across the embedded array — no extra queries.

raw_aggregate projects a year and a per-question vote total ($sum across the embedded choices array). Results come back as Question instances with the extra computed attributes attached.

Atlas Search with a fallback


class SearchView(TemplateView):
    template_name = "polls/search.html"

    def get_context_data(self, **kwargs):
        ctx = super().get_context_data(**kwargs)
        q = (self.request.GET.get("q") or "").strip()
        ctx["q"], ctx["results"], ctx["mode"] = q, [], "none"
        if not q:
            return ctx
        try:
            from django_mongodb_backend.expressions.search import SearchText
            ctx["results"] = list(
                Question.objects.annotate(_search=SearchText("polls_question_search", q))
            )
            ctx["mode"] = "atlas"
        except Exception:
            ctx["results"] = list(Question.objects.filter(question_text__icontains=q))
            ctx["mode"] = "fallback"
        return ctx

Atlas: $search. Local replica set: __icontains + a banner.

On Atlas, SearchText hits the $search index. On a local replica set, falls back to __icontains and surfaces a "fallback" banner in the template — same view, no crash in dev.

medical_records/models.py


from django.db import models
from django_mongodb_backend.models import EmbeddedModel
from django_mongodb_backend.fields import (
    EmbeddedModelField,
    EncryptedEmbeddedModelField,
    EncryptedCharField,
)


class Patient(models.Model):
    patient_name = models.CharField(max_length=255)
    patient_id = models.BigIntegerField()
    patient_record = EmbeddedModelField("PatientRecord")


class PatientRecord(EmbeddedModel):
    ssn = EncryptedCharField(max_length=11)
    billing = EncryptedEmbeddedModelField("Billing")
    bill_amount = models.DecimalField(max_digits=10, decimal_places=2)


class Billing(EmbeddedModel):
    cc_type = models.CharField(max_length=50)
    cc_number = models.CharField(max_length=20)

Encrypted fields are declared like any other field — no schema gymnastics in app code.

Patient → PatientRecord → Billing, all via EmbeddedModelField. The sensitive bits (ssn, billing) use Encrypted* variants; everything else is stock Django.

Build Python objects exactly as you would without QE — libmongocrypt encrypts marked fields before they leave the client, decrypts on read. ssn and billing appear as ciphertext on disk; other fields remain readable.

EncryptedRouter


# project/routers.py
from django_mongodb_backend.utils import model_has_encrypted_fields


class EncryptedRouter:
    """Route models with encrypted fields to the 'encrypted' DB."""

    def db_for_read(self, model, **hints):
        if model_has_encrypted_fields(model):
            return "encrypted"
        return "default"

    db_for_write = db_for_read

    def allow_migrate(self, db, app_label, model_name=None, **hints):
        if hints.get("model"):
            if model_has_encrypted_fields(hints["model"]):
                return db == "encrypted"
            return db == "default"
        return None

Add to DATABASE_ROUTERS — reads/writes find the right DB automatically (no using=). Migrations still run per-database: migrate + migrate --database encrypted; allow_migrate just decides which models apply to each.

model_has_encrypted_fields walks a model's fields for any Encrypted* variant. db_for_read/write routes queries automatically (no using= needed). Run migrate twice — once per alias — allow_migrate ensures each invocation only touches the right models.

Don't skip migrate --database encrypted

If the encrypted collection doesn't exist yet, the first insert creates it — as a plain, unencrypted collection. So create_patients guards against it:


def _encrypted_collections_exist(self):
    conn = connections["encrypted"]
    conn.ensure_connection()
    return "medical_records_patient" in conn.database.list_collection_names()

if not options["skip_checks"] and not self._encrypted_collections_exist():
    self.stderr.write("Encrypted collections do not exist. "
                      "Run 'manage.py migrate --database encrypted' first.")
    return
          

# Demonstrate the foot-gun on purpose:
python manage.py create_patients 5 --skip-checks
QE only activates when the collection is created with encryptedFields metadata — that happens during migrate. Skip it and MongoDB creates a plain collection; SSNs land in plaintext. The preflight check guards against this. --skip-checks lets you demo the failure mode deliberately.
